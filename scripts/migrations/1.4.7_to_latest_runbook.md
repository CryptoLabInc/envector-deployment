## 1. 배경

머지 cutover는 "S3에 `.bin` 파일 쓰기 → pending shards 행 INSERT → cutover TX" 순서로 진행됩니다.
`.bin` 파일 쓰기가 영속 의도 기록(shards 행)보다 먼저 커밋되므로, 그 사이 하드 크래시가 나면
어느 DB 테이블에도 참조가 없는 추적 불가능한 `.bin` 파일이 남습니다.

`created_shard_list`는 `.bin` 파일 쓰기 전에 destination shardID를 task_queue 행에 영속
기록하는 intent-first 앵커입니다. 기동 시 reclaim 스윕이 "미완료(종료 전) 앵커 + shards 행 부재"를
참조 없는 것으로 판정해 `.bin` 파일을 회수합니다.

⚠️ 본 SQL은 application binary(앵커 기록 + 기동 스윕)와 **한 배포 단위로 묶여야** 합니다.
컬럼만 추가하고 신 binary가 없으면 앵커가 기록되지 않아 무의미합니다.

### 1-1. (shard_id, row_idx) 인덱스 (Step 6)

`getItemIdFromIdMap`는 검색 결과의 `(shard_id, row_idx)`를 매 검색마다 `item_id`로 해석합니다.
플래너가 쓸 수 있는 인덱스가 없으면 이 해석이 `item_shard_map` 전체 Seq Scan이 됩니다.
1.4.0-1.4.4 / 1.4.5-1.4.6 스크립트(Step 6, app-stop 구간)와 `createShardMapTable`(신규 install)에는
이미 반영됐으나, 1.4.7-alpha 인스턴스의 **기존 인덱스**는 두 경로를 거치지 않았으므로 여기서 백필합니다.

- **full(비-partial) 인덱스**여야 합니다: 쿼리에 `deprecated=FALSE` 술어가 없어(soft-delete 분류를 위해)
  partial은 플래너가 못 씁니다 — #1936에서 옛 `row_idx_alive` partial이 제거된 이유와 동일. full은 사용 가능(실측 1M 해석 215ms→1.4ms, 검색 QPS conc1 +94%).
- **CONCURRENTLY**로 생성하므로 라이브 인스턴스의 쓰기를 막지 않습니다. 따라서 트랜잭션 **밖**에서
  실행되며(`CREATE INDEX CONCURRENTLY`는 BEGIN/COMMIT 안에서 거부됨), `\gexec`가 테이블별로 autocommit 실행합니다.

⚠️ **CONCURRENTLY 중단 시 INVALID 인덱스 잔류**: 빌드가 중간에 끊기면 무효 인덱스가 남고,
재실행의 `IF NOT EXISTS`가 그 무효 인덱스를 "존재"로 보고 건너뛰어 영구 잔류할 수 있습니다.
재실행 전 아래로 무효 인덱스를 먼저 제거하십시오:

```sql
SELECT format('DROP INDEX IF EXISTS %I;', c.relname)
FROM   pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE  c.relname LIKE 'idx\_%\_item\_shard\_map\_shard\_row' AND NOT i.indisvalid
\gexec
```

### 1-2. index_operations.orphaned_blob_paths 앵커 + (operation_type, state) 인덱스

update 스왑 TX는 교체된 항목의 옛 blob과 스왑에서 패배한 새 blob 목록을 커밋과 원자적으로
`orphaned_blob_paths`에 기록합니다. 정상 경로는 post-commit 회수 성공 직후 비우고, 그 사이 크래시가
나면 앵커가 살아남아 기동/주기 스윕(`sweepOrphanedUpdateBlobs`)이 회수합니다. 앵커가 없으면
크래시 시 회수 대상 목록이 사라져 옛 암호문이 스토리지에 영구 잔존합니다.

`(operation_type, state)` 인덱스는 update reconciliation 스윕(`MERGE_PENDING` update 스캔)과
기동 backstop이 매 사이클 이 쌍으로 조회하므로 필요합니다. 인덱스 이름은 GORM 태그
(`idx_index_operations_type_state`)와 일치시켜 신규 install(initSchema)과 업그레이드가 수렴합니다.
`item_shard_map` 인덱스와 동일한 INVALID-인덱스 회복 절차가 적용됩니다:

```sql
DROP INDEX IF EXISTS idx_index_operations_type_state;  -- indisvalid=f 인 경우만
```

⚠️ 본 SQL은 application binary(앵커 기록·clear + 스윕)와 **한 배포 단위로 묶여야** 합니다.
컬럼만 추가하고 신 binary가 없으면 앵커가 기록되지 않아 무의미합니다.

### 1-3. shards.row_add_count (single insert 즉시 검색)

단건 insert가 row를 기존 raw shard의 EVI accumulator에 직접 append한 횟수입니다. 두 가지 역할을
합니다.

- **용량 상한**: accumulator는 RLWE 다항식 차수(1024)로 제한되므로 `num_vectors` 여유와 무관하게
  1024회에서 append를 거부합니다.
- **shard 종류 판별**: `> 0` 이면 appended raw shard로 간주되어 merge cutover가 일반 merge
  source가 아닌 overlap buffer로 취급합니다(흡수된 row만 숨기고 live row가 0일 때 retire).

merge로만 자라는 기존 shard는 기본값 0이라 backfill이 필요 없습니다. 컬럼이 없으면 append 경로가
기동하지 않으므로 신 binary와 **한 배포 단위로 묶어야** 합니다.

## 3. 검증

```sql
-- (1) task_queue 컬럼
SELECT column_name, data_type, column_default
FROM   information_schema.columns
WHERE  table_name = 'task_queue' AND column_name IN ('created_shard_list', 'operation_type');
-- → created_shard_list(text, default ''), operation_type(text, default 없음) 두 행이면 성공.

-- (2) index_operations 컬럼
SELECT column_name, data_type, column_default
FROM   information_schema.columns
WHERE  table_name = 'index_operations' AND column_name = 'orphaned_blob_paths';
-- → orphaned_blob_paths(text, default '') 한 행이면 성공.

-- (2') shards 컬럼
SELECT column_name, data_type, is_nullable, column_default
FROM   information_schema.columns
WHERE  table_name = 'shards' AND column_name = 'row_add_count';
-- → row_add_count(bigint, NOT NULL, default 0) 한 행이면 성공.

-- (3) (operation_type, state) 인덱스가 VALID로 존재하는지
SELECT c.relname AS index_name, i.indisvalid
FROM   pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE  c.relname = 'idx_index_operations_type_state';
-- → 1행, indisvalid = t 여야 성공. f면 위 DROP 후 재실행.

-- (4) 모든 item_shard_map에 shard_row 인덱스가 VALID로 존재하는지
SELECT c.relname AS index_name, i.indisvalid
FROM   pg_class c JOIN pg_index i ON i.indexrelid = c.oid
WHERE  c.relname LIKE 'idx\_%\_item\_shard\_map\_shard\_row'
ORDER BY c.relname;
-- → item_shard_map 테이블마다 1행, indisvalid = t 여야 성공. f가 있으면 위 무효-인덱스 제거 후 재실행.
```

## 4. 롤백

신 binary는 빈 앵커('')를 무시하므로 컬럼을 남겨둔 채 구 binary로 롤백해도 무해합니다.
컬럼 제거가 필요하면 진행 중 dispatch가 없는지(앵커가 모두 비어 있는지) 먼저 검증하십시오.
in-flight 상태에서 컬럼을 제거하면 회수 단서가 사라져 고아 `.bin`이 영구 잔류합니다.

```sql
-- 결과가 0이어야 DROP 안전. 0이 아니면 진행 중 dispatch가 있으므로 DROP 금지.
SELECT count(*) FROM task_queue WHERE created_shard_list <> '';
```

```sql
ALTER TABLE task_queue DROP COLUMN IF EXISTS created_shard_list;
```

`operation_type`은 NULL 허용 판별자로, 값이 없으면 `TargetShardID` 휴리스틱으로 폴백하므로
컬럼을 남겨둔 채 구 binary로 롤백해도 무해합니다. 제거가 필요하면:

```sql
ALTER TABLE task_queue DROP COLUMN IF EXISTS operation_type;
```

`orphaned_blob_paths`는 구 binary가 읽지 않으므로 컬럼을 남긴 채 롤백해도 무해합니다. 제거는
회수 미완료 앵커가 없을 때만 안전합니다(제거하면 회수 단서가 사라져 옛 암호문이 영구 잔존):

```sql
-- 결과가 0이어야 DROP 안전.
SELECT count(*) FROM index_operations WHERE orphaned_blob_paths <> '';
```

```sql
ALTER TABLE index_operations DROP COLUMN IF EXISTS orphaned_blob_paths;
DROP INDEX IF EXISTS idx_index_operations_type_state;
```

`row_add_count`는 구 binary가 읽지 않으므로 컬럼을 남긴 채 롤백해도 무해하며, **남겨두는 쪽을
권장합니다**. appended raw shard가 남은 상태에서 제거하면 구 binary가 그것을 일반 raw shard로
오인해 cutover에서 통째로 retire시키고 append된 row가 유실됩니다. 제거는 그런 shard가 없을 때만
안전합니다:

```sql
-- 결과가 0이어야 DROP 안전. 0이 아니면 append된 row가 남아 있으므로 DROP 금지.
SELECT count(*) FROM shards WHERE row_add_count > 0;
```

```sql
ALTER TABLE shards DROP COLUMN IF EXISTS row_add_count;
```
